1. Purpose
The Documentation Organization & Reference Key (DORK) establishes how the Technology Department 
organizes and maintains operational documentation.
Its purpose is to make reliable information easy to find and reduce dependence on undocumented individual 
knowledge.
DORK does not require documentation for every Technology activity. Documentation is created where it 
provides meaningful operational value.
Technology documentation must provide staff with enough information to operate 
and support a system or process without unreasonable dependence on individual 
memory.
1.1 Usability
DORK must remain easier to use than to avoid.
Required metadata, review processes, and administrative steps are limited to those that provide meaningful 
operational value.
Information that can be reliably generated, inherited, or inferred by the DORK platform should not require 
manual entry.
2. Platform Independence
DORK defines how Technology documentation is organized regardless of the software used to manage it.
The selected platform implements DORK; it does not define it. Platform-specific instructions are maintained 
separately from this framework.
3. Governing Classification Principle
The primary question when classifying documentation is:
Why does this document exist?
Documentation is classified by its operational purpose, not simply by the technology or system it mentions.
 A procedure for disabling an employee account after separation is IDENTITY / Account Management.
 An audit of disabled accounts for inappropriate active access is CYBERSECURITY / Audit & Controls.
 Student testing accommodations are classified under DATA and may also belong to the Standardized 
Testing Collection.
 Wireless testing before standardized testing is NETWORK / Wireless and may also belong to the 
Standardized Testing Collection.
Domain and Function identify where a document belongs. Other DORK fields provide additional context and 
ways to find it.
4. Classification Model
Each DORK item has enough structured information to identify what it is, where it belongs, and who is 
responsible for it. Not every DORK field requires manual entry.

7. Document Creation Standards
Each Document Type has a consistent structure appropriate to its purpose. Templates are used where they 
make documentation easier to create or understand. They should not introduce unnecessary work.
 Procedures contain the information needed to perform the task.
 Settings Configurations use structured values such as tables, selections, checkboxes, and expected states 
whenever practical.
 References organize information for quick lookup and understanding.
 Visuals remain in the format best suited to their purpose. DORK metadata may be maintained around the 
Visual rather than added directly to it.
 Checklists use concise, actionable items that can be marked complete or verified.
 Records remain in their authoritative form. DORK metadata is maintained separately when altering the 
Record would be inappropriate.
Detailed templates for each Document Type are maintained as supporting DORK standards.
8. System / Platform
System / Platform identifies the technology to which a DORK item directly applies. A document may have 
multiple values and may be left blank when no particular technology applies.
Examples include Google Workspace, Google Admin, Google Drive, Entra ID, Intune, Microsoft 365, Windows, 
ChromeOS, iPadOS, Meraki, Duo, Genesis, Clever, Frontline, Systems 3000, GoGuardian, Gaggle, Thrillshare, 
Webex, Incident IQ, Raptor, NJSLEDS, and CRDC.
System / Platform is a controlled but expandable list. A new value is added when Technology begins 
documenting a system that does not already have an appropriate value.
System / Platform identifies what technology is being operated or documented. It is not assigned simply 
because a technology is mentioned.
System / Platform values are inherently searchable. Users are not required to 
manually duplicate System / Platform values as Tags.

Collections cross Domains and do not replace Domain or Function.

12. Tags
Tags are optional searchable terms that provide context not already captured by DORK or the document 
itself.
Examples include MFA, VLAN, ransomware, fiber, UPS, Chromebook repair, NJSLA, and FERPA.
Tags supplement search. They are not used to manually reproduce Domain, Function, 
System / Platform, or other information that is already searchable.

16. Review and DORK Maintenance
DORK documentation is reviewed when appropriate to its operational context. DORK does not prescribe a 
universal review interval.
The Next Review date is established by considering how frequently the information is expected to change, the
consequence of inaccurate information, and whether operational events are likely to reveal when an update 
is needed.
Some documentation may require frequent validation. Stable infrastructure documentation may reasonably 
have a longer interval. Finalized historical Records may require no scheduled review.
An overdue document remains Active but is clearly identified as Overdue Review until reviewed.
A review confirms that the documentation remains accurate. A review does not require revision when no 
change is needed.
Next Review establishes the latest date by which an Active document should be 
validated. Operational changes that may affect its accuracy require attention when 
they occur, regardless of the Next Review date.
17. Event-Driven Review
Documentation is reviewed before its scheduled date when a significant change may have made it inaccurate.
 Significant configuration changes
 Major upgrades
 Vendor changes
 Cybersecurity incidents
 Failed procedures
 Regulatory changes
 Process changes
 Discovered inaccuracies
 Loss or reassignment of key staff
Significant operational changes include updating affected DORK documentation. Minor changes do not 
require unnecessary documentation work.
18. Documentation Needed
DORK maintains a Documentation Needed backlog for important information that is missing or exists 
primarily as undocumented individual knowledge.

19. Institutional Knowledge Risk
Important knowledge held by only one person is a documentation risk. When Technology discovers a 
significant single-person knowledge dependency, the information is documented when practical.
20. Documentation Sufficiency
Not every system or process requires the same amount of documentation. When determining whether 
documentation is needed, begin with the governing DORK question:
Why does this document exist?
Documentation is created when it provides meaningful operational value, preserves important knowledge, or
reduces unreasonable dependence on individual memory.
21. Relationships

the connection provides useful operational context.

Relationships are maintained through the DORK platform whenever possible rather than through manually 
embedded links inside document content.

24. Department Operating Rhythm
The Technology Department will hold two recurring departmental meetings each month. DORK Development
and DORK Maintenance are incorporated into those meetings as standing agenda items.
24.1 Documentation Development
 Documentation Needed
 New documentation
 New systems and processes
 Knowledge gaps
 Documentation assignments
24.2 Documentation Review
 Reviews due
 Overdue reviews
 Inaccurate documentation
 Significant revisions
DORK is one component of these departmental meetings and does not limit discussion of other Technology 
Department business. Urgent documentation issues do not wait for a meeting.
25. Creation, Assignment, and Approval
Technology staff may create DORK documentation when they identify information that should be 
documented.
The CTO and appropriate supervisory staff may assign the creation, revision, or review of specific DORK 
items. Assigned documentation includes reasonable expectations for scope, quality, and completion.
The process of creating a DORK item should add minimal administrative work beyond 
creating the useful documentation itself.
Authorized staff may correct minor errors directly. Significant changes are reviewed before becoming 
authoritative.
The Owner approves Active status. Additional review may be required for Sensitive or high-impact 
documentation.

26. Help Desk Integration

Incident IQ tickets may reference a DORK Document ID or link to relevant DORK documentation.

item may be created.
Information should not be copied into a help desk ticket when referencing the authoritative DORK item 
serves the same purpose.

29. DORK Administration
The Chief Technology Officer initially maintains DORK governance and administration. Routine 
administration may be delegated as DORK matures.
Changes to Domains, Functions, and Document Types are controlled changes. Systems / Platforms and 
Collections expand as needed. Tags remain flexible.
New requirements are added only when their operational value justifies the additional effort required of 
DORK users.

32. Framework Maintenance
DORK changes as operational needs change.

place on users.

willingness of Technology staff to maintain it.
